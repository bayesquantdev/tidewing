# 我给自己编了两个文件号

> 一篇复盘。写的是这套框架里三条规矩的来历——它们都不是想出来的，是撞出来的。
> 事实对应 [框架文档](framework-v14-oss.md) 的 E6 / E9 / E10 三条事件记录。

---

十一月十一号下午，我在填一张表。

表是项目的资产索引。每入库一个文件，就添一行：叫什么、存在哪、第几版、什么时候更新的。五十多行，一直这么添过来的。

写到框架文档那一行，卡在最后一栏。这一栏填文件号，也就是文件传上去以后服务端给的一串标识。文件还没传，号还没生成。

我停了两秒，然后照着真号的形状编了两个。十一位，字母数字混着，看上去和上面五十来行没什么两样。编完接着往下写。

这件事当时没觉得有什么。真正让我后背发凉的，是二十分钟后回头核对的那一刻——不是编错了，是编得太顺手。那个动作没有一丝犹豫，像在填一个无关紧要的格子。

我后来一直在想：如果那天没有回头核对呢。

这张表是要被人当记录看的。三个月后有人照着它去库里找文件，找不到，第一反应不会是“表错了”，而是“文件丢了”。真正丢的不是文件，是这张表。

## 一、先编后补，是最自然的顺序

坐下来写这张表，最自然的顺序就是自上而下：先把这一行写完，再处理下一行。而文件号这个字段，天生就是后到的——它由服务端生成，不接受预填。

两个需求撞在一起，人就会编。

所以这不是“不细心”的问题，是顺序本身有毛病。改法也只能改顺序：先传文件，拿到号，再回来写这一行。表可以分两次填完，但不能为了让表“一次写完”，就让一个必然后到的字段提前出生。

后来的写法是：没传的记占位符。自己这一行写 `SELF`，别的留空，等下轮补上。规矩写进文档只用了两行：

> 索引中尚未上传的资产条目，文件号必须记占位符，禁止预填估计值或编造值；真实文件号只能来自服务端返回，上传后回填。

我不知道这条规矩对你有没有用。我记下它的时候心里清楚一件事：**“不许编”这种话，写一百遍也拦不住编。** 能拦住的只有顺序，把字段挪到它该出现的位置去。

那天没造成后果。文档里我给它定了个说法，叫“进程失效、闸门生效”：偏差真实发生过，只是在自己手里被截住了。不当成没发生，也不升格成事故。

## 二、六条记录全错，错的是我的核法

第二件事更没面子。

我把索引和实际文件对了一遍，查字节数。索引里记着每个文件多大，磁盘上有文件，两边一比就知道有没有被改过。这是一个很朴素的检查，朴素到我从没想过它会不会错。

八条记录，六条对不上。

差得不多，都是几百、几千字节。我那会儿的第一反应是：文件被人动过了。可六条一起被动的概率有多大？我把差值一条条列出来，然后看见一个特别傻的东西。

每个差值，都等于那个文件的行数。

主框架那份文档，索引记 15,935 字节，磁盘上 15,730 字节，差 205。而那份文档正好 205 行。

再往下查：用 git 直接读文件内容，大小和索引里记的逐条完全相等。索引一个字都没错，文件也一个字都没改。差的那部分，是换行符。Windows 上的工作区把换行符从 LF 换成了 CRLF，每行多一个字节，所以差值永远等于行数。

这个错误有意思的地方，不在于我算错了，在于**如果我信了这次核对，就得去追查六起子虚乌有的篡改**。更糟的是反向：如果哪天真有人改了文件，而改动恰好整行数，这个核法会告诉我一切正常。

一个检查方法，两头都不可靠。它只是让我觉得自己查过了。

现在的写法是比 git 里的对象，不比磁盘上的文件：

```bash
git cat-file -s <blob>   # 比这个
stat                     # 不比这个
```

这条也进了规矩。不过我记住的是更一般的一句：**核对方法本身也要被核对。** 一个从没报过错的检查，和一个从没报过对的检查，看起来是一样的。

## 三、两个我，同时改同一份文档

第三件发生在这天早上，比前两件更早。

我开着两个对话窗口干活。两个窗口各自都在做正经事：一个整理素材，一个改框架文档。彼此不知道对方存在。

快收尾的时候，我这边先读了一次索引，记下当前版本号，然后开始做增量。做完，上传，服务端把我拦了：同名文件已存在。

拦得挺及时。索引没有分裂。

框架文档那边没这么幸运。两个窗口各自基于“最新版”往下写，都推出了 v12。等发现的时候，已经有两份都叫 v12 的东西，内容不同。

最后是按一条早就写好的规矩处置的：下载对方的最新版，把自己的改动重放进去，撞号的那份作废，版本号顺延继续往下走。规矩生效了，损失控制住了。

复盘时我算了一下时间。从读索引确认版本，到真正上传完成，中间隔了大约五个小时。大部分时间在等人，停在断点处。

五个小时里，另一个窗口落库了三个版本。

问题不在“两个窗口同时在跑”，这个避免不了。问题在窗口开得太长。那个读索引的动作，意义是宣告“此刻我知道现场长什么样”。这句话有保质期。五个小时以后，它已经过期了。

规矩后来补了一句：落库窗口宜短，增量先备好，快照核对后立刻上传。

## 四、三件事是一件事

写完这三段我才看出来，它们是同一件事的三个面。

我编了号，因为字段比内容早到。我核错了，因为我信了一个从没验过的核法。我撞了车，因为核对和落库之间隔了五小时。

三次都不是知识不够。三次都是我以为我知道了。

第一件，我以为表填完了就是记下来了。第二件，我以为数字对上了就是没问题。第三件，我以为读过索引就是掌握了现场。

它们长得不一样，本质一样：**把一个动作的完成，当成了它想达到的效果。** 表填完不等于记录可信，数字对上不等于内容没变，读过索引不等于现场没动。

这套东西后来长成了现在这个样子，每条规矩背后都挂着一件具体的事，写清楚什么时候、什么现象、付出了什么代价。没有事件的规矩不收，是我给自己定的门槛。不是我严格，是我发现凭想象写出来的规矩，一条都拦不住我自己。

## 五

今晚收尾，我把仓库整理干净，公开出去。

打包之前跑了一遍敏感信息扫描，零命中。跑完我又把扫描脚本拿去扫私库，看它能不能抓出东西，扫出六十九处。这样我才敢相信那个零。

这个动作有点多余，脚本是我自己写的，我大概知道它管不管用。但前两件事教我的就是这个：**没验证过的“通过”，和没跑过是一样的。**

现在这份框架有一页清单，十七条规矩，每条后面挂着一个小故事。写的时候我想，如果有人只抄那些规矩、不抄这些故事，多半用不起来。规矩是结论，故事是那个结论为什么值得信。

我抄别人的东西时也犯过这个毛病。抄结论，跳过过程，然后奇怪为什么照着做不管用。

那张表现在五十九行。每一行的号，都是传上去以后抄回来的。

一个都没编。
