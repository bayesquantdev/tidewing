## 一、底层约束：一切设计的出发点

大模型有两个根本约束，两个视频的所有建议都由此展开：

1. **模型本身没有记忆**。所谓"记得"，依赖智能体记录的聊天历史（上下文）。
2. **上下文窗口有限，且有压缩机制**。塞得太多 → 重要信息被压缩丢失；同时 Token 消耗过快 → 成本上升。

由此得出两条推论：
- **新旧任务不要放在同一个上下文里聊**，一个上下文干一件事。
- **背景信息和流程要脱离会话独立存在**（写成文件、写成 Skill），智能体之间才能无缝接手——这就是"多智能体协作"能够成立的前提。

## 二、逻辑框架：五个层次

```
┌─────────────────────────────────────────┐
│  调度层  调度 skill：统一管理、协调各任务  │
│         + 确认点编排（何时暂停等人）      │
├─────────────────────────────────────────┤
│  任务层  具体任务 → 独立 skill 模块       │
│         （选题 / 写文案 / 剪视频 / 简历筛选）│
├─────────────────────────────────────────┤
│  隔离层  独立上下文：主 Agent 控多个子 Agent│
│         （写与审分离，防"灯下黑"）         │
├─────────────────────────────────────────┤
│  记忆层  Agent.md（项目背景·共享记忆）     │
│         state.json（任务进度）            │
│         log.md（操作日志·报错记录）        │
│         assets.json（资产索引）           │
├─────────────────────────────────────────┤
│  兜底层  Git 版本控制 + 私有远端托管       │
│         （代码与文档同管：误删/故障可找回）│
└─────────────────────────────────────────┘
```

### 1. 任务层：任务拆分，打包成 Skill 模块
- 把具体任务分别写成**独立的 skill 模块**，例如自媒体的"选题 / 写文案 / 剪视频"、HR 的"简历筛选"。
- 把重复任务从日常对话中拆出来固化，下次直接调用，省去反复交代背景。
- **任务契约三要素（v5 补，来自 MetaGPT SOP / CrewAI `expected_output`）**：每个任务模块应写清"目标、输出格式、边界（不碰什么）"。第三项最容易被省略，也最容易出问题——缺边界的任务会把"顺手做了什么"当成产出交上来。
- **第四要素：落点（v6 新增，D4 决议，来源：技能包审核）**：契约还须写明产出物落哪里——报告落到哪个文件或哪件资产、进度写进哪份 `state.json`、失败写进哪份 `log.md`。三要素只回答"交什么"，不回答"交到哪"；缺落点时，O4"索引随入库同步"没有可挂靠的动作，只能靠人记。审核对象 `github-project-scout` 即典型：输出模板写得完整，但产出报告无归档路径、无状态落点（见审核报告 P1-1 / P1-2）。

### 2. 调度层：引入"调度 skill"，并定义确认点
- 单个 skill 只会干活，不会管事。引入一个**调度 skill**，统一管理和协调各个具体 skill。
- 这是"多智能体"的第一形态：一个大脑（调度）+ 多双手（任务 skill）。
- **确认点编排（v3 新增，Q1 决议）**：调度层还负责决定"何时暂停等人确认、何时自动放行"。判断标准：**有外部副作用**（写远端、覆盖资产、对外发送）的动作必须设确认点；纯读操作自动放行。
- **外部副作用的第四类：本机环境写入（v6 补，D1 边界澄清）**：装依赖（`pip` / `npm`）、执行第三方脚本、改环境变量或注册表，改的是本机而非项目盘，同样属外部副作用，同样必须设确认点。原三项列举只覆盖"写到项目外的远端"，漏了"写到项目外的本机"。这里要分清"查看"与"确认"：**看过内容再执行，不等于取得同意**——审核对象 `github-project-scout` 的安全红线要求"先查看内容"，却没有要求"先问用户"，正是这个缺口（见审核报告 P0-2）。
- 确认点与 O3 配合：一次产出只设一个确认点，复核与归档合并为一问。
- **确认点的位置约束（v5 新增，来源：LangGraph 中断语义复核）**：确认点必须落在**两次写入之间**，不能落在一次写入的中途。原因见 O13 候选条。另外，确认触发时应先把进度写进 `state.json` 再提问——"暂停"要落在文件上，不能只落在对话里。

### 3. 记忆层：四个文件，各管一摊（v3 起由三文件扩展）
| 文件 | 职责 | 对应问题 |
|---|---|---|
| `Agent.md` | 项目概况、目录结构等背景信息，可让 AI 自动总结生成 | 跨智能体切换时"知不知道项目是什么" |
| `state.json` | 记录各任务执行进度（进行中 / 已完成） | 流程中断或调度时"进行到哪一步" |
| `log.md` | 操作日志、报错信息 | 出错后"哪里坏了、为什么坏" |
| `assets.json` | 资产索引：文件名、file_id、版本、状态 | "有哪些资产、版本对应哪个 file_id" |

要点：状态和日志**用结构化文件存，不靠聊天记录**——上下文可以被丢弃，文件始终在。索引与背景分离存放：背景变化慢（`Agent.md`），索引每次入库都变（`assets.json`），混在一起会导致高频改动污染背景文档。

**变更频率分层原则（v4 新增，来源：实践验证 #2 事件 E4）**：分层不止发生在文件之间，**也必须下探到单个文件内部**——任何支撑文档的字段都按变更频率区分：慢变条款（规则、结构、方法论）留在文中；快变数据（清单、file_id、版本号、进度）外置为引用，**不在文中留快照**。判据很简单：*如果一个小改动就要求人或 AI 重新粘贴、复制某个文档，说明这份文档混装了快变内容。*

**索引字段口径（v5 新增，来源：实践验证 #3 事件 E6）**：
- `size` 字段的口径是**版本库内对象的字节数（LF 换行）**，不是工作区磁盘字节数。Windows 下 `core.autocrlf=true` 会在检出时把 LF 转成 CRLF，磁盘字节比库内多出"行数"那么多。
- 因此校验必须用 `git cat-file -s <blob>` 或 `git ls-tree -l`，**禁止用工作区 `stat` 结果比对索引**（详见 O14）。
- `name` 字段必须等于**落库时的实际文件名**，版本记在 `version` 字段，不进文件名。索引名带 `-v7` 而仓库文件名不带，会导致按名检索断链（Q9 观察项）。

### 4. 隔离层：主 Agent 控多个子 Agent，防"灯下黑"
- 单一上下文里"自己写自己审"，审核必然不严——写的人对自己的产出有盲区。
- 解法：**写文案和审文案放在不同的独立上下文里**，由主 Agent 控制多个子 Agent 分工执行。
- 每个子 Agent 上下文干净、职责单一，审核视角更客观。这是框架中最能体现"多智能体"价值的一层。

**模型异构分工（v10 新增，来源：素材稿《主模型子模型协作-汇总整理.md》，视频③）**：写与审不仅可分上下文，还可分**模型档位**——把关方（设计、审核、验收）用高思考档旗舰模型（思考级别开到最大），执行方（编码等具体任务）用低成本模型，分工的第一动机是 Token 成本（全旗舰编程的费用难以承受）。视频口诀「先分工，再把关」。**落地门槛低**：Kimi Code 可设 secondary model，Claude Code / Codex 用子 Agent 方式配置，主流编程 Agent 已原生支持添加多个 provider（DeepSeek、Moonshot、Zhipu 等）。**强度辨析**：视频语境的「主模型验收」发生在同一会话（写审同上下文，省成本、防明显错误）；本项目 Q8 的独立上下文审阅更严（防灯下黑，样本 #3、#4 已实证两类自查盲区）。两者可共存：日常编码用前者把关，结论层文档仍走 Q8 独立审阅。本条为素材推导的结构性补充，未经项目内实践验证，不占 O 编号。

**判定权归属与机检标准（v12 新增，来源：素材稿《OpenLoop MAS-框架逻辑分析-汇总整理.md》，外部实现 tffgwy/openloop-mas v0.1.0，作者归属未证实；状态候选，转正条件见 Q13）**：写与审分离解决「谁来审」，本条解决「**判定权在谁手里**」。判定权在模型手里，模型说「好了」就是好了，不可复现、不可审计；判定权在确定性规则手里，同一份产物加同一份标准永远得到同一结论。**前提**：审阅前须有逐项验收标准清单（机检规则，或明示该条由模型判定并要求附证据），无清单先补标准再审。具体三条：① **机检优先**——可写成机器可判定规则的验收标准，一律写成机检规则（外部实现支持八类：contains / not_contains / min_chars / max_chars / regex / lines_min / section / json_keys，据其 README 机检规则表，2026-11-11 13:06 读取），规则判定结果压过模型自评；② **未判定即不通过**——审阅回执必须逐项对应验收标准给出判定，缺项按不通过处理，不得因「看起来可以」放行。此条**补 Q8 未覆盖的「回执未给判定」情形**：Q8 现行「逐条处置」指审阅发现的采纳/拒绝留痕（生效要求不变），本条针对的是审阅方沉默放行的缺口（候选期内不改变 Q8 任何生效条款）；③ **写不出机检规则不是硬编的理由**——那说明目标本身还没想清楚，正确动作是拆细目标，或明确接受该条由模型判定并要求附证据。**与 Q8 的关系（互补定位，用户裁决 2026-11-11）**：机检审「结构可判定」的部分，Q8 独立上下文审阅审「判断是否成立」的部分。外部实现的一个直接证据：其五角色中的 lead（闭合裁决）在代码里从未被调用，闭合决策完全由确定性规则完成，系统照样闭合——判定权上移到规则是有效的；但该实现同模型自审、无人工闸门、机检标准本身写得松时引擎照放（绿灯可复现但标准可能没价值），故不能替代 Q8，只能补 Q8 的量化缺口。**实现瑕疵备忘（素材稿代码级核实）**：该实现同时存在 verifier 无条件调用（即使全部标准带机检仍多耗一次模型调用）与 token 预算少计 planner 用量两处瑕疵——机检省下的钱可能被冗余调用吃回，收编其机制时应按本项目会话成本重新核算。

**边界条件（v5 新增三条，来源：实践验证 #3 首次触发隔离层；v9 扩为四条，S2）**：

前三条边界必须写死，否则这一层会退化成"多个上下文互相污染"；第四条为 v9 增补候选：

1. **写入必须串行**。并行只用于只读与审阅。多个 Agent 同时改同一份产出，各自的隐式决策（命名、风格、边界处理）会在合并时才冲突。这是四条中唯此一条有外部证据反复确认。
2. **审阅方只读**。审阅 Agent 不得写入任何文件；所有写入回到主流程串行执行。
3. **只给产出物，不给推理链**。审阅方若拿到作者的思路，就会顺着思路找证据，而不是从成品反推规格——那正是"灯下黑"换了个位置。
4. **驳回必须附问题、位置与修改方向（v9 新增，S2 落框架；状态候选，转正条件见本条末）**：**驳回≠否决**——只写「不通过」而无具体问题与修改方向，作者只能靠猜。史实参照（据来源转述）：门下省「涂归」即给事中在诏敕上涂窜删改后奏还重拟（学界对其对象有争议：唐前期主要针对上行奏抄，宋人窄化为对下行制敕的封驳审查，本文取通行归纳口径）。框架内对应为「只读批注」：审阅方在回执中逐处指明位置与改法，不动原稿；回执为会话回复，由主流程转录进修订记录，审阅方不落盘（边界 2 的全称禁令不变）。**转正条件**：本项目出现第一例「审阅意见笼统导致无效往返」；转正前，本条为审阅方的质量要求——建议执行，不作强制闸门。

**收益与成本（v5 新增，实测数据；v8 补第二例）**：
- 收益：样本 #3 中，独立审阅方在无作者上下文条件下指出 10 项问题，其中 3 项阻断级；**2 项属作者单上下文不可能自查的类型**（无出处的量化断言、把未发生的问题写成已发生的因果）。这两类的共同点是：不是知识错误，而是"自己相信自己写的推论"。
- **第二条收益：用量成本（v14 新增，来源：素材稿《主Agent子Agent成本优化-汇总整理.md》，视频⑤）**：隔离不只防灯下黑，也省 Token。子 Agent 在独立新环境运行，**不继承主 Agent 的历史上下文**，只接收必要的关键信息；任务完成把结果交回。效果是主 Agent 上下文增长极慢，减少与大模型的高频交互次数，支撑低成本、低干预的长期自动化运行。与 v10 的「模型异构分工」正交互补：异构分工省**单价**（每个 token 多少钱），上下文隔离省**用量**（一共消耗多少 token），两者可叠加。反向印证：全部工作挤在单一主上下文里，上下文持续累积，很快耗尽额度且频繁需要人工干预。本条为素材推导，未经项目用量实测，不占 O 编号。
- **第二例（样本 #4，2026-11-10）**：《三省六部制多智能体协作可行性分析-v1.md》未经审阅入库，当日补审发现 2 项阻断级 + 4 项重要级 + 3 项建议级（审阅判定"修订后可用"，详见该文档 v2 修订记录 R1–R9）。关键证据：样本 #3 确认的两类自查盲区——无出处断言（"运行了一千三百余年"）、来源层级混用（把二手来源的重构当原始文献口径转述，且该二手来源自身的品级错误被逐字带入）——**再次由审阅方而非作者发现**。Q8 预设的升级条件（第二例）满足。
- 成本：往返约 25 分钟；审阅方独立抓取外部数据时**消耗了共享额度**（样本 #3 本轮因此有两处数据只能标"未取"）。另据外部文献，多智能体 token 消耗可达单 Agent 的数倍量级。
- 因此（Q8 于 v8 升格，见决议记录）：**结论层文档**（要作为决策依据的产出）**入库前必须经一次独立上下文审阅**；日常操作与素材稿不适用。用在一份随手记的笔记上，成本大于收益。

### 5. 兜底层：Git 版本控制（代码与文档同管）
- 全项目用 Git 管理，推送至 GitHub / Gitee 等远端，**仓库必须为私有**。
- **文档类资产同样纳入 Git（v3 新增，Q3 决议）**：不只管代码。纯文本 md 体量极小，代价可忽略，收益是每次修改都有不可变快照。
- 即使电脑损坏或 AI 误删重要文件，也能找回；O5 的"留版本"由机制替代人工命名。
- **提交即推送纪律**：每次资产入库后同步 `commit + push`，保持「本地工作区 / 项目资产 / 远端仓库」三处一致；三处分叉即视为流程未完成。
- **闭环止损与终态枚举（v12 新增，来源同隔离层 v12 条款；状态候选，转正条件见 Q13）**：兜底层原管「误删可找回」（Git），本条扩到「**流程停不下来时怎么止损**」。三条：① **终态用枚举，禁用形容词**——任何一次审阅、一轮迭代的收尾状态只能是枚举值：通过 / 驳回修订 / 升级人工裁决，不存在「差不多完成」。写法借鉴外部实现的四态枚举（closed / escalated / budget_exhausted / error）；本项目取三态——预算耗尽与错误两态在本项目语境并入「升级人工裁决」前的过程留痕，不单设终态；② **停滞检测作止损信号**——同一问题连续多轮往返、审阅意见文本逐字相同，判定无效循环，升级人工裁决，不再加轮次。外部实现按产物 SHA-256 连续 3 轮相同判卡死；据其方法论文档原文（docs/loop-engineering.md，2026-11-11 13:06 读取），作者将停滞检测定位为「省钱项」而非优化项——「如果产物在连续几轮里一模一样，那多给 10 轮只是多烧 10 轮的钱」（原文转述）；③ **升级必带上下文**——升级人工时附目标、验收标准、最后一版产出、未决问题清单，保证人工一句话能接着裁（对应外部实现的工单 resume 机制）。与 Q8 既有阈值（复审连续两轮未过升人工裁决）的关系：停滞检测是补充信号，两者**取先触发者**；量化阈值待本项目实践标定，由 Q13 监测。
- **Tag 做不可变快照（v5 建议）**：文件名带版本号会被误改，annotated tag 不会。tag 命名与索引 `version` 字段对齐，避免两套版本体系并存。
- 参考实例：本项目远端为 GitHub 私有仓库（示例记法 `git@github.com:<user>/<repo>.git`），索引登记在 `assets.json` 的 `remote_repo` 字段。

## 三、演进路径：从单会话到多智能体

```
第 0 阶段：单会话硬扛
  → 上下文爆炸、成本高、越聊越忘
        ▼
第 1 阶段：任务拆分 + Skill 化
  → 重复流程固化，随时调用
        ▼
第 2 阶段：加记忆层（Agent.md / state.json / log.md / assets.json）
  → 背景与状态脱离会话存在，跨智能体可接手
        ▼
第 3 阶段：引入调度 skill
  → 多个 skill 由一个大脑统一编排，形成工作流
        ▼
第 4 阶段：主 Agent + 多子 Agent
  → 写/审分离，独立上下文，产出更客观
        ▼
持续迭代：不断打磨规则（见第四节）
```

**执行层子框架备用预案：OpenLoop MAS（v13 新增，状态：候选预案；登记依据：用户裁决 2026-11-11「确认开发需求/把对方框架/定位成/执行层面的子框架/补充进现有框架/备用」，按用户原话分句照录；决议记录见 D5）**

- **定位**：外部实现 tffgwy/openloop-mas（v0.1.0；**作者归属未证实；其能力、性能与验收结论均为作者自述**——仓库当日开源、0★、无第三方验证）作为本框架的**执行面（垂直运行面）预案**（下称「执行面」；用户裁决原话为「执行层面的子框架」，见 D5），只补「单任务内的机器闭环」：实链条为 planner → worker → verifier（逐条判 pass/fail + 证据）→（仅失败时）reflector，第五位 lead 为保留接口、代码未调用（见隔离层 v12 条款）；引擎提供机检执行、终态落盘、账本记账的具体实现。主框架管协作纪律、记忆与人工闸门；子框架只补单任务内的机器闭环。
- **边界判据（v13 结构审读结论）**：①「执行面」是五层之外的**垂直运行面**，不参与五层编号、不构成第六层；本预案不是演进阶段，第三节阶段序列不含它；② 归入执行面的唯一判据是「单任务内 + 全部验收标准带机检规则 + 无外部副作用 + 闭合不依赖人工判断（升级人工为例外出口，不视为闭合手段）」，不满足者仍走任务层/调度层（该加严仅适用于引擎执行段，不改 v12 条款效力）；③ 本预案登记于演进路径仅因「启用时机」属演进问题，与阶段递进无关。
- **条款与实现分层**：v12 收编走「素材稿 A1–A3 三条候选 → 合并为两条条款（隔离层「判定权归属与机检标准」、兜底层「闭环止损与终态枚举」）+ Q13 观察项」。条款是**纪律要求**，与引擎是否启用无关，候选期内照常按 Q13 独立转正；引擎只是该纪律的一种**实现手段**，备用状态不改变纪律效力。本预案收的是整体作为可调用引擎的部分（源码、install 脚本、团队模板、随包 SKILL.md，均为其自述交付形态）。
- **激活条件（三条须全部满足；判定人为用户，判定结论记 `log.md`）**：① 验收标准全部带机检规则且条数 ≥3（门限为本预案自设，待首个激活事件校准；机检覆盖不了「判断是否成立」的条目视为不满足本条）；② 已按演进路径第 1 阶段完成 Skill 化，且单次执行的人工核对成本仍不可接受——**不得以激活代替 Skill 化**；③ 任务内无外部副作用动作（写远端、覆盖资产、对外发送、装依赖、执行第三方脚本）。激活后首轮即关闭的，记一次「不必要激活」，计入撤销判断。
- **激活纪律（七条）**：① 激活须人工裁决，一次任务一激活，不常驻、不默认启用；② 激活前**借用 Q8 的独立上下文形式**做预审（借用形式，不构成 Q8 适用范围的扩张；预审对象为本次任务的验收标准清单与任务边界），版本核对以远端 tag 或 commit hash 为准，核对结果与所用版本一并记入 `log.md`；③ 对外引用须带两条并列标注——「作者归属未证实」「能力、性能与验收结论均为作者自述（当日开源、0★、无第三方验证）」，引用「零依赖」「一键安装」「四道止损」等自述能力时后者不得省略；④ 子框架运行账本（append-only，自动落盘）是过程留痕，**不构成第二权威源**：主框架 `log.md` / `state.json` / 资产索引是唯一权威源，激活任务收尾须把终态、工单号、产物哈希、逐条判定摘要回填主框架并登记落点，冲突以主框架为准；⑤ 首次安装/升级（install.sh / install.ps1）属本机环境写入（D1 边界第四类），执行前单独确认；⑥ 任务内确需外部副作用动作时，由主流程在子框架之外设确认点，不得交由引擎自理；⑦ 未满足激活条件前维持备用，不做预防性启用（与运维层「规则须由真实事件触发」同纪律）。
- **撤销条件（满足其一即撤销登记并在版本行留痕；「预期」指机检判定与人工复核结论一致且未触发停滞升级，判定人为用户）**：① 主框架自建 skill 已覆盖同类任务；② 外部仓库归档、删除或长期不再维护；③ 连续两次激活均未达预期；④ 「不必要激活」累计两例。

## 四、运维层：搭建只是开始，打磨才是重点

视频②特别强调：初期生成的内容通常有瑕疵，**工作流的价值不在"搭起来"，而在后续反复调整规则、持续优化**，才能达到理想效果。

实操建议：
- 每次跑完工作流，检查 `log.md` 里的报错和不理想产出；
- 把发现的问题**写成规则**，回写进对应 skill 或调度逻辑；
- 小步修改、跑一轮、验证一轮，避免一次改太多无法定位回退原因。

**规则状态分两级（v5 新增）**：

- **生效**：有真实失效事件支撑，可直接执行。
- **候选**：有证据或推演支撑，但触发条件尚未出现。候选规则只作观察靶点，不要求执行。

**O14 的事件记录（E6）**：核对索引时发现磁盘字节与 `size` 不一致，8 条中 6 条有差。差值逐条等于文件行数（如主框架 15,935−15,730=205=205 行），且 git blob 大小与索引 `size` 逐条完全相等。根因 `core.autocrlf=true`。若按"磁盘 ≠ 索引即视为篡改"执行校验，会 100% 误报；反向也危险——真篡改若恰好差出整数行数会被判正常。

**O12 / O13 为何仍是候选**：两条都由外部证据推导，本项目尚未出现对应失效。按自我验证原则不能准入；但它们是下一样本的观察靶点。

### 运维层的自我验证原则（v2 新增，v5 补并列路径）

运维层的规则**只能用真实流程验证**，不能靠推演新增。每条 O 规则必须附带：触发它的具体失效事件、可复现的判断条件、验证通过的标准。无失效事件支撑的规则，暂不进运维层。

**并列路径（v5 新增，来源：实践验证 #3 的 F4）**：上述原则对**预防性规则**存在盲区——若规则本身就是禁止某类操作（如 O12 禁止并行写入），则规则一旦生效，失效就永不发生，准入条件自相矛盾。

因此补充一条并列路径：**预防性规则可以凭"需求出现且串行化产生可观测代价"这类近失效事件准入，不必等失效真实发生。** 限制条件三条，缺一不可：

1. 近失效事件必须**已实际发生并被记录**（时间、现象、代价），不能是设想；
2. 必须能说明**如果不加规则，下一步会发生什么**；
3. 规则必须写明**撤销条件**——代价消失即退回候选。

## 六、决议记录（原「待讨论」，v3 已裁决）

三项结构性缺口均于 2026-11-09 裁决，决议如下：

### D1（原 Q1）：人工确认点归入调度层 ✓
**决议**：确认点编排属调度层职责，不新增层次。
**判断标准**：有外部副作用（写远端、覆盖资产、对外发送）→ 必须暂停确认；纯读操作 → 自动放行。

### D2（原 Q2）：记忆层新增 `assets.json` ✓
**决议**：记忆层由三文件扩为四文件，新增资产索引 `assets.json`（字段：name / file_id / version / size / role / status）。
**理由**：背景（变化慢）与索引（每次入库都变）频率差异大，混在 `Agent.md` 会导致高频改动污染背景文档；独立 JSON 可程序化追加，人为误改风险低。
**约束**：索引只增不删，历史版本置 `status=archived`；不回填索引视为流程未完成（与 O4 一致）。

### D3（原 Q3）：文档类资产纳入 Git ✓（已执行）
**决议**：兜底层同时管理代码与文档；远端仓库必须私有；建立"提交即推送"纪律，保持本地 / 资产 / 远端三处一致。

|---|---|---|
| D1 外部副作用 → 设确认点 | 5 次资产写入零重复打断 | 一次指令跑完全程，未出现重复打断 |
| D2 记忆层四文件分离 | 分离有效，暴露"需下探到单文件内部" | 分层有效，但校验口径出问题（E6） |
| D3 文档纳入 Git | 三次版本升级可回溯 | v1/v2 并存，可逐条比对修订是否落实 |

**样本量增至 3，但仍不能称为普适规律**：三个样本同属"文档与资产操作 + 研究写作"域，跨域（内容生产、代码开发）未验证。**隔离层到样本 #3 才第一次被真正触发**——前两个样本对它的"验证"是空缺，这一点在 v5 中更正。

### D4（v6 新增）：任务契约增第四要素「落点」 ✓
**决议**：任务层契约由三要素（目标 / 输出格式 / 边界）扩为四要素，增「落点」——产出落到哪个文件或资产、进度写哪份 `state.json`、失败写哪份 `log.md`。
**依据**：审核 `github-project-scout` 技能包时发现，其契约三要素齐全，但产出报告无归档路径、无状态落点、无日志落点。这不是该模块独有的问题——本项目三个样本的流程同样是"产出即入库"，而契约从未写明入库动作由谁在哪个环节触发，O4 只能依赖人记。
**性质**：结构性补全，**未经失效事件验证**，与 O 规则不同轨，不占 O 编号。若第二个 skill 复现同一缺口，按 Q11 转正为 O 规则。

### Q4（v4 新增，待外部条件）：长令牌传输能否工具化？
手工转录 >1500 字符的签名在三次操作中三次出错（E3），项目内只能靠 O9 校验缓解，无法根治。需平台提供"工具直接完成传输、调用方只接收 file_id"的能力。**当前无法裁决，挂起。**
**v5 补充**：样本 #3 出现一次同类但不同因的失效（漏发签名头），进一步说明失败模式不止"转录错"一种，手工环节的每个字段都是风险点。

### Q5（v4 新增）：索引"最高版本号"解析是否该脚本化？ ✓
**v5 裁决：已脚本化，可固化。** 样本 #3 已用脚本读取 `assets-v*.json`、按版本号取最高、比对条目数，运行期无人工判断。
**前置条件须写明**：版本号排序必须是语义化排序（`v1.10` > `v1.9`），字符串排序会排错。

### Q6（v5 新增，已裁决）：候选 O14 是否准入？ ✓
**裁决：准入，状态为生效。** 依据 E6：真实发生、根因可复现、后果可指认（误报导致不必要重传；漏报导致篡改被放过）。

### Q7（v5 新增，已采纳）：可行性判定是否统一用四级 A/B/C/D？ ✓
**采纳为研究类文档的写法规范**（非 O 规则，属文档规范）：各级须有明确门槛，每行须附"判定改变的触发条件"，避免"中高""可低成本试"这类不可证伪的措辞。
附注：可随时按用户意见撤销或改档，不构成硬约束。

### Q8（v5 新增观察，v8 升格）✓
**v8 裁决：升格为默认流程。** 结论层文档（要作为决策依据的产出）入库前必须经一次独立上下文审阅，审阅发现逐条处置并留修订记录；执行沿用隔离层生效的前三条边界（写入串行、审阅方只读、只给产出物不给推理链；第四条候选，暂不并入 Q8 强制执行）。
**触发证据（第二例）**：原观察条款预设「若后续出现第二例，则升级为默认」——2026-11-10《三省六部制多智能体协作可行性分析-v1.md》入库时标注"未经独立审阅"，当日补审发现 2 阻断 / 4 重要 / 3 建议，其中样本 #3 确认的两类自查盲区再次由审阅方而非作者发现。条件满足，本次裁决属机械执行预设条款，非新增裁量。
**成本收益**：约 25 分钟/份 + 共享额度消耗；两例实测（样本 #3、#4）审阅方均发现了作者单上下文不可能自查的问题，收益两次成立。
**首轮实测（v9，样本 #5，2026-11-10）**：Q8 强制流程首次执行——初审 2 阻断 / 7 重要 / 8 建议，17 条全部采纳或折中处置（其中 B2 据审阅意见将新条款降为候选）；修订后复审 1 轮通过，复审另贡献 1 重要 + 5 建议（同批处置）；全程约 10 分钟（08:04–08:14，两次独立审阅 + 修订），远低于 25 分钟估额。
**撤销条件**：连续两份结论层文档审阅未发现任何阻断或重要级问题、且时间成本明显大于收益时，可复议降回观察项。
**执行细则（v9 补，S2 落框架，随边界 4 一并候选）**：修订稿复审由主流程（调度层）发起，必须用新的独立上下文；复审输入＝修订稿＋前次审阅问题清单，不含作者的处置理由（处置理由属作者推理链，受边界 3 约束）；轮次与结论记入 `log.md`。若转正，复审连续两轮未通过即升级人工裁决，不设无界循环——政事堂的历史动因正是「两省反反复复、既费功夫又误事」（据来源转述），教训是写前对齐优于事后多轮驳回。Q8 的「逐条处置」含拒绝处置：拒绝采纳同样留记录，不得静默丢弃（此为 Q8 既有要求的具体化，非新增义务）。

### Q9（v5 新增，观察）：索引 `name` 与落库文件名不一致
索引登记 `项目配置指令-多智能体协作-v7.md`，仓库实为 `项目配置指令-多智能体协作.md`（字节一致、名称不一致）。只出现一次，先登记。若再出现，升级为 O 规则（版本只进 `version` 字段）。

### Q10（v6 新增，观察）：判定阈值是否必须单一权威源？
**现象**：`github-project-scout` 把同一套判定口径写了三遍——`references/repo-evaluation.md`（5 处阈值表述）、`scripts/repo_report.py`（3 处代码阈值）、`assets/manual-template.html`（评分卡 + 一句"一项不达标就换下一个"）。实测产出 3 处不一致：三项达标仅缺 License 被判"不建议"、400 天未提交被判"不建议"、已归档仓库被判"谨慎"。
**暂不立规的原因**：这是静态审查发现，不是运行失效事件。按运维层自我验证原则，O 规则须由真实失效触发；本次的"失效"是审出来的，不是跑出来的。
**拟议规则**（若触发）：判定阈值只在一处定义（代码读配置），文档只引用不复述，模板不承载判定。
**触发条件**：第二次出现"代码与文档口径不一致，且已导致对外输出错误"。

### Q11（v6 新增，观察）：任务层 skill 缺产出物落点是否升为 O 规则？
同 D4。当前只有 `github-project-scout` 一例。若第二个 skill 出现"产出无归档路径、无状态落点、无日志落点"，则 D4 由结构条款转正为 O 规则，并须附真实失效事件。

### Q12（v7 新增，观察）：并行会话的增量文档是否独立登记为资产？
O16 规定过程中只产增量（delta 文档、Q/O 提案）。增量本身是否作为独立资产入索引登记，还是只作为框架版本的中间产物随版本落库不单独登记？当前全部增量均走后者。若出现"某增量被多个后续会话反复引用、脱离主框架单独使用"，则升级为独立登记。等第二例，同 Q11 的克制。

### Q13（v12 新增，观察）：「判定权归属」与「闭环止损」候选条款的转正条件
**观察内容**：隔离层「判定权归属与机检标准」与兜底层「闭环止损与终态枚举」两条为素材推导（来源：外部实现 OpenLoop MAS，tffgwy/openloop-mas，作者归属未证实），未经本项目实践验证，按素材稿条款惯例不占 O 编号、状态候选。
**转正条件（逐条映射，各转各的，不联动）**：
- 隔离层条款（判定权归属）：本项目出现第一例「审阅回执缺项 / 未给判定仍放行」的事件 → 转正为 O 规则；
- 兜底层停滞检测项：本项目出现第一例「同一问题连续往返、审阅意见文本逐字相同导致无效轮次」的事件 → 该项转正；
- 兜底层终态枚举项：本项目出现第一例结论记录收尾混入「差不多完成」类非枚举表述 → 该项转正。
转正后按运维层准入程序升为 O 规则，并附真实失效事件记录。
**与 Q8 候选边界 4 的关系**：边界 4 盯「审阅意见笼统」，本条盯「回执缺项」与「往返不停」——三者共同覆盖「无效往返」的三种成因，互不替代。
**克制条款**：机检规则只兜结构，兜不住判断质量；不得因本条把「判断是否成立」也硬编成规则，否则会产生「格式对即结论对」的假绿灯（外部实现同款风险，见隔离层条款）。
**与执行层子框架预案的关系（v13 补）**：v12 并入的两条候选条款及其转正条件是**纪律要求**，候选期内照常各转各的，不受本预案影响；预案激活后的实际运行记录（如机检规则在真实任务中的判定效果）可作为转正条件的观察素材，但激活事件本身不计为失效事件。

### D5（v13 新增）：OpenLoop MAS 定位为执行层子框架备用预案 ✓（候选预案）
**决议**：用户裁决（2026-11-11 15:48，原话「确认开发需求/把对方框架/定位成/执行层面的子框架/补充进现有框架/备用」按原话分句照录）：将外部实现 OpenLoop MAS（tffgwy/openloop-mas，作者归属未证实）定位为执行层子框架，备用。
**比选（v13 = v12 收编 + 整体登记，v12 条款不变）**：整体登记不占五层条款位、登记于第三节「演进路径」；用户确认该方向（2026-11-11 15:58「继续推进」）。本 D5 按时间追加于 Q13 之后。
**约束**：不占 O 编号、不占五层条款位、不预防性启用；激活条件、激活纪律与撤销条件见第三节预案块。
**状态**：候选预案，未经激活验证。
