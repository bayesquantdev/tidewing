# 落地检查清单（一页版）

> 从框架文档 §四、§五 抽出，压成一页，供直接照抄。
> 论证过程与失效事件出处见 [框架文档](framework-v14-oss.md)，本文只留「该做什么」。
> 摘录时间 2026-11-11，对应框架 v14。

---

## 一、搭之前：六问

没通过的先别搭，搭了也是返工。

1. **重复任务拆成独立模块了吗？** 同一段提示词贴到第三次，就该做成 skill。
2. **有统一编排，还是各干各的？** 没有编排，模块之间的交接处必然掉东西。
3. **项目根目录有 `Agent.md` 吗？** 不写下来，上下文压缩一次就没了。
4. **有 `state.json` 和 `log.md` 吗？** 进度和报错分开存，别指望会话记忆。
5. **写与审用了独立上下文吗？** 同一个上下文既写又审，等于没审。
6. **项目 Git 化并推到远端了吗？** 本地仓库只防手滑，不防硬盘。

## 二、每次落库：六步

顺序不能换，尤其是「先上传、后登记」——反过来就必然编造标识。

| 步 | 动作 | 判据 |
|---|---|---|
| 1 | **查目录**：有无并发写入、有无重名 | 同名冲突要在写之前发现，不是写的时候 |
| 2 | **写入**，取服务端返回的真实标识 | 标识只能来自返回值，不能估、不能编 |
| 3 | **校验**：逐字节 diff 或 blob 哈希 | 不看命令退出码；字节数比较要区分换行符 |
| 4 | **版本化**：新文件名带版本号，不覆盖旧版 | 旧版保留，索引里标 archived |
| 5 | **登记索引**：文件名 + 标识 + 版本 + 日期 | 尚未上传的，标识记 `SELF` 或留空 |
| 6 | **复核推送**：`git rev-parse HEAD` vs `origin/main` | 退出码为 0 不代表已推上去 |

---

## 三、会话收尾：五项

会话结束 ≠ 落库。这一步不做，产出就散了。

- [ ] 本会话的成果文件都入库了吗？（不是留在临时目录）
- [ ] 索引登记了吗？（缺索引视同未完成）
- [ ] 工作副本提交并推送了吗？（`git log origin/main..main` 应为空）
- [ ] 临时文件清了吗？（含 token 的配置文件、下载的中间件）
- [ ] 下一会话需要接着做的事，写下来了吗？

## 四、17 条规则速查

每条都由一次真实事故逼出来。「状态」为**候选**的，说明触发条件尚未出现，只作观察点、不强制。

| 编号 | 一句话 | 状态 |
|---|---|---|
| O1 | 资产流程按「申请 → 传输 → 落库」三段显式声明，中断后可断点续做 | 生效 |
| O2 | 含超长令牌/签名的机械操作交给工具，主对话只收结论字段 | 生效 |
| O3 | 一次产出只设一个确认点，复核与归档合并成一问 | 生效 |
| O4 | 索引随入库同步更新，索引失真即流程未完成 | 生效 |
| O5 | 覆盖前先留版本，禁止裸覆盖 | 生效 |
| O6 | Windows 中文路径直传，不写 `.ps1`/`.bat` 中转（编码会坏） | 生效 |
| O7 | 一律版本化新文件；确需覆盖时事后核对 name/size/mtime | 生效 |
| O8 | 文件引用自身标识用占位符，下轮回填，不写估计值 | 生效 |
| O9 | 长令牌传输不看退出码，校验 HTTP 码与返回体；签名失效须重申请 | 生效 |
| O10 | 文档不内嵌高频变更内容（清单/版本号/状态段），慢变与快变分文件 | 生效 |
| O11 | 推送后用 `rev-parse` 比对 HEAD 与 origin | 生效 |
| O12 | 并行只用于只读与审阅，写入必须串行 | 候选 |
| O13 | 确认点前先落 `state.json`；确认点须落在两次写入之间 | 候选 |
| O14 | 字节数校验用 `git cat-file -s`/`git ls-tree -l`，不用工作区 `stat` | 生效 |
| O15 | 会话收尾盘点本会话产出是否全部落库 | 生效 |
| O16 | 并行会话用「快照-增量-落库」三段式；版本号永不预占，落库时顺延 | 生效 |
| O17 | 未上传条目的标识记占位符，禁止预填估计值或编造值 | 生效 |

**三条最容易漏的**：O8（自指必用占位符）、O11（推送必复核）、O14（比字节要选对口径）。这三条的共同点——都失败在「以为成功了」。

## 五、其余硬规矩

这些不成体系但都会咬人，原清单里逐条挂着。

| 主题 | 要求 |
|---|---|
| **迭代循环** | 跑完 → 读 `log.md` 复盘 → 改规则。小步改、跑一轮验一轮，一次改太多就无法定位回退原因 |
| **任务模块三件套** | 做什么 + **不碰什么** + 产出物落点（报告 / state / log 各落哪）。缺"不碰什么"，子 Agent 就会顺手改别的 |
| **隔离层四条边界** | 写入串行 / 审阅只读 / 只给产出物 / 驳回附「问题 + 位置 + 修改方向」（第四条候选） |
| **索引口径** | `name` 等于落库文件名，版本只记在 `version` 字段——不要把版本写进文件名后再抄进 name |
| **环境写入** | 装依赖、跑第三方脚本这类动本机的操作，**先问再做**，不是看完就执行 |
| **模板参数化** | 日期用占位符（`{{TODAY}}`），"输出前记得替换"是人工纪律，不算合规 |
| **结论层独立审阅** | 结论性文档入库前过一遍独立上下文；审阅发现逐条处置并留修订记录。复审由主流程发起，同样独立上下文，记入 `log.md` |
| **模型档位异构** | 把关方（审）用旗舰高思考档，执行方（写）用低成本模型。同档互审容易一起漏 |
| **子 Agent 传参** | 只给必要关键信息，不继承主上下文——这是成本控制，不是洁癖 |
| **机检优先** | 可机检的验收标准写成规则，判定权在规则而非模型自评。模型说"差不多完成了"不算通过 |
| **逐项验收** | 审阅前有验收清单，回执逐项对应判定，缺项按不通过处理 |
| **终态枚举** | 每轮收尾状态只能是：通过 / 驳回修订 / 升级人工裁决。禁用"基本完成""差不多" |

## 六、加规则的门槛

这一条比上面 17 条都重要。规则会越加越多，门槛不立，最后没人执行。

一条规则要写进运维层，必须同时具备三样：

1. **触发它的具体失效事件**——时间、现象、代价，缺一样不算。
2. **可复现的判断条件**——什么情况下必然违规，能说清才有可执行性。
3. **验证通过的标准**——怎么算改好了。

**没有失效事件支撑的规则，暂不进运维层。**

唯一的例外是**预防性规则**（本身禁止某类操作，规则一生效，失效就永不发生，自相矛盾）。走并列路径准入，三个限制缺一不可：

1. 近失效事件**已实际发生并记录**，不是设想；
2. 能说明**不加规则下一步会发生什么**；
3. 写明**撤销条件**——代价消失即退回候选。
