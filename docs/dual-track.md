# 双轨同步：资产盘与 git 的分工

## 为什么要有这一页

同一份内容同时存在于三个地方，如果不讲清谁说了算，分叉就会从例外变成常态。本项目的做法是：**允许三处并存，但裁决权唯一**。这一页写的就是这个唯一裁决权归谁、以及每次落库要做哪几步。

## 三处存储，三种职责

| 位置 | 角色 | 谁在改 | 对外可见 |
|---|---|---|---|
| 资产盘（项目协作盘） | 协作入口与索引登记处。非 git 用户也能读 | 人 + agent，经上传工具 | 否 |
| 私有 git 远端（地址从略） | **版本真相**。完整历史、内部素材、裁决记录 | commit | 否 |
| 公开仓库 | 对外裁剪版。只含方法论最小集 | 公开 commit / PR | 是 |

三处的关系不是镜像，是**同一内容的三种形态**：资产盘要的是「随时能打开」，私有远端要的是「能回滚、能追责」，公开仓库要的是「能给别人看」。

## 三条流向，都是单向

**1. 落库流（写作 → 资产盘 → 私有远端）**

```
本地写作 → 上传资产盘取真实 file_id → 回填索引 → 私有远端同步副本
```

上传在登记之前，不能反过来——先写索引再上传，就会出现「索引里写着、盘上没有」的悬空条目；为图省事编个形似真实 ID 的占位串，则是 E9 事件的原型。

**2. 发布流（私有远端 → 发布暂存 → 公开仓库）**

```
私有远端 → 裁剪（去内部地址、占位化真实 ID、补致谢） → 发布暂存目录 → 公开仓库
```

裁剪是必经步骤，不是可选步骤。私有远端里的内容是研究过程，公开仓库里的是结论——两者的差别不在篇幅，在是否含内部基础设施信息。

**3. 索引流（只在资产盘与私有远端之间）**

资产索引不对外、不进公开仓库。它是内部账本，公开仓库的版本口径由 `CHANGELOG.md` 承担，两者不混用。

## 冲突时谁说话

**私有 git 历史 > 资产盘副本 > 发布暂存目录。**

理由很实在：git 有不可变历史，能证明某个时点是什么样；资产盘副本和暂存放的是拷贝，拷贝没有历史。所以当三处内容不一致时，以私有远端某个 commit 为准，另外两处向它对齐——而不是反过来让 git 去迁就盘上的版本。

## 三条禁令

1. **不把资产盘原文件直接推向公开仓库。** 少了裁剪这一步，内部地址和真实 ID 会跟着出去，而公开之后历史不可改写。
2. **不把公开仓库的裁剪内容回写私有远端。** 裁剪版是减法，回写等于用删过的版本覆盖全量版，内部素材会丢。
3. **不用同名覆盖推进索引。** 索引与指令类文件更新一律以带版本号的新文件入库，旧版转 `archived` 并保留（O7）。同名覆盖过一次，就再也说不清哪一版是哪一版。

## 一次落库的检查清单

按顺序做，不要跳步：

1. **上传前查目录**——确认没有并行会话刚写过（O16）。
2. **上传后回下载核对**——逐字节比对，不只看接口返回成功。
3. **先取 file_id 再写索引**——索引里禁止预填估计值（O17）。
4. **索引新建文件，旧版归档**——并回填旧版的实际 file_id（O7 / O8）。
5. **提交后推送，再核一遍**——`git log origin/main..main` 为空才算推完；「提交成功」不等于「推送成功」。
6. **三处一致性核对**——至少核对索引与框架文档的字节数，不一致就停下查原因。

## 已知的偏离（不算事故，记录在案）

- 内部研究版的历史版本（v2–v13）只在私有远端与资产盘，不进公开仓库。公开侧的可追溯性由文档头部的版本段承担。
- 私有远端缺少若干早期资产条目（早期索引 v1.1–v1.3、部分打包形态的文件），属建库时间线造成的形态差异，不是丢件。这类差异**不回填**——留着能看出仓库是什么时候建的。

## 出处

- O4（入库后必须同步索引）、O5 / O7（只增不删、带版本号新建）、O8（自引用 file_id 记 SELF，下一版回填）、O16（并行会话快照-增量-落库）、O17（未入库条目禁预填 file_id）。
- E9（预填编造 file_id，落库前自查纠正）、E10（并行会话撞号，增量重放）。
